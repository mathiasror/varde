Why varde

Less in the image,
less to defend.

A varde — the Norwegian cairn, a stack of stones that marks a trail — carries only the stones that mark the way. These images carry only what your app needs to run.

  • Distroless

    Production images ship no shell, no package manager, no coreutils. Just the runtime — nothing for an attacker to pivot through. The one exception: postgres's static ash, which initdb requires.

  • Non-root by default

    Every container runs as uid/gid 1000:1000 in a /app it owns. Nothing runs as root unless you explicitly override the user.

  • Multi-arch

    Native linux/amd64 and linux/arm64, selectable by tag (e.g. :21-musl-arm64). Same image, your architecture.

  • Scannable by design

    A distroless image has no OS package DB — so a Nix-closure CycloneDX SBOM covers system packages and the runtime. Scan it with grype.

  • Built with Nix

    Reproducible builds from a committed lockfile. A weekly lock-bump commit flows CVE fixes through — every image traces to a commit.

  • Drop your app in

    Bring one real artifact — a fat JAR, a binary, code plus its deps — and add two lines of Dockerfile. The entrypoint runs it directly.

Usage

Two lines on top of your build.

Build your artifact in a stage that has the tooling, then COPY it onto varde. There's no shell, so the entrypoint runs your app directly.

Dockerfile · Spring Boot / fat JAR 
# build stage: Gradle bootJar -> one self-contained fat jar
FROM gradle:8.14-jdk21 AS build
WORKDIR /home/gradle/src
COPY --chown=gradle:gradle . .
RUN gradle bootJar --no-daemon

FROM ghcr.io/mathiasror/varde-jre:21
# base ENTRYPOINT is /runtime/bin/java, CMD ["-jar", "/app/app.jar"] — just place the jar
# (override CMD to add JVM flags; they must come before -jar)
COPY --from=build /home/gradle/src/build/libs/app.jar /app/app.jar
Dockerfile · interpreter + deps 
# deps stage: alpine = musl, matching the default musl runtime
FROM python:3.14-alpine AS deps
WORKDIR /build
COPY requirements.txt .
RUN pip install --no-cache-dir --target=/app/site-packages -r requirements.txt

FROM ghcr.io/mathiasror/varde-python:3.14
COPY --from=deps /app/site-packages /app/site-packages
COPY main.py /app/main.py
# no shell to "activate a venv" — put the deps on the import path
ENV PYTHONPATH=/app/site-packages
Dockerfile · runtime + node_modules 
# deps stage: alpine = musl, so native addons match the runtime
FROM node:24-alpine AS deps
WORKDIR /build
COPY package*.json ./
RUN npm ci --omit=dev

FROM ghcr.io/mathiasror/varde-node:24
COPY --from=deps /build/node_modules /app/node_modules
COPY src/ /app/src/
# no npm start — point CMD straight at a real file
CMD ["/app/src/server.js"]
Dockerfile · static binary 
# build stage: CGO_ENABLED=0 -> a fully static binary
FROM golang:1-bookworm AS build
WORKDIR /src
COPY . .
RUN CGO_ENABLED=0 go build -trimpath -ldflags="-s -w" -o /out/app .

FROM ghcr.io/mathiasror/varde-static:latest
# base ENTRYPOINT is /app/app — just drop the binary in
COPY --from=build /out/app /app/app
Dockerfile · glibc binary 
# build stage: a default cargo build links glibc -> varde-glibc
FROM rust:1-bookworm AS build
WORKDIR /src
COPY . .
RUN cargo build --release --locked

FROM ghcr.io/mathiasror/varde-glibc:latest
# base ENTRYPOINT is /app/app — just drop the binary in
COPY --from=build /src/target/release/app /app/app
Dockerfile · static site on :8080 
FROM ghcr.io/mathiasror/varde-nginx:latest
COPY site/ /app/
# serves /app on :8080, non-root
Dockerfile · redis + config 
FROM ghcr.io/mathiasror/varde-redis:latest
# for -p 6379:6379 the conf must set requirepass (or protected-mode no on trusted networks)
COPY redis.conf /app/redis.conf
CMD ["/app/redis.conf"]

Built with Nix

Every stone accounted for.

Nix builds each image from an exact dependency closure. That same closure becomes the SBOM — so what grype scans is precisely what's in the image, down to glibc and zlib.

  1. Reproducible closure

    Nix pins the exact runtime and system libraries — and only those.

  3. Exact CycloneDX SBOM

    syft reads the closure out of the image into a CycloneDX SBOM with CPEs.

  5. grype scans it all

    System packages and runtime are scannable — not just your app deps.

Supply chain

Signed, attested,
verifiable.

Every image is keyless-signed with Sigstore cosign from one identity: the repo's build.yml workflow on main. No long-lived keys, and every signature is in the public Rekor transparency log. A tag only moves to a digest after its signature and attestations are attached and verified.

On every per-arch image

  • cosign signature — on the per-arch images and the multi-arch lists, so verifying by tag works
  • CycloneDX SBOM with exact NVD identities, attached to the image
  • OpenVEX — CVEs fixed by nixpkgs patches or reviewed as not affecting the image, with evidence
  • Vulnerability-scan attestation — CI's signed grype result, as a point-in-time snapshot
  • SLSA build provenance — builder, source commit, invocation

The SBOM, OpenVEX, scan and provenance attestations live on the per-arch digests. The supply-chain section of the README shows how to verify and extract each one, and how to apply the VEX when you scan.

FAQ

Questions, answered.

What is a distroless container image?

An image that carries only what an application needs at runtime, such as the language runtime and the libraries it links against, and none of a Linux distribution's userland: no shell, no package manager, no coreutils, no busybox. With less in the image there is less for an attacker to use and less to patch.

How is varde different from Google's distroless images?

Neither ships a shell or a package manager in its production images (varde's one exception is PostgreSQL's static ash, which initdb requires). varde builds every image with Nix instead of from Debian packages, defaults to musl with glibc one tag away, runs as non-root (1000:1000) by default, and also covers services: nginx, Redis, PostgreSQL, MySQL, RabbitMQ and Memcached. See the full comparison.

Why does Trivy report zero vulnerabilities on a varde image?

That is a false negative. Trivy, Docker Scout and Snyk find packages through a distro package database or language package URLs, and none of them understands Nix, so they see no packages at all. Use grype, which reads the Nix store paths in the image and matches them against NVD by CPE, or load the attested CycloneDX SBOM into Dependency-Track.

How do I verify that a varde image is authentic?

Every image is keyless-signed with cosign using the GitHub Actions OIDC identity of the repository's build.yml workflow on main, and the signatures are recorded in the public Rekor transparency log. Run cosign verify with that certificate identity and issuer, as shown in the verification example. The per-arch digests also carry CycloneDX SBOM, OpenVEX, vulnerability-scan and SLSA build-provenance attestations, which cosign verify-attestation and gh attestation verify check.

Should I use musl or glibc?

Start with the bare tag, which is musl: a smaller libc means less to patch. Append -glibc to the tag when something needs glibc, such as a Python wheel that only ships manylinux binaries, a native Node addon built against glibc, or a prebuilt dependency that assumes glibc.

How often are the images updated?

Weekly. A scheduled job bumps the pinned nixpkgs revision in flake.lock, commits it to main and rebuilds every image from that commit, so CVE fixes flow through and every published image traces back to a commit whose lockfile reproduces it.

Is varde free to use commercially?

Yes. The build definitions are Apache-2.0, and the images are public on GitHub Container Registry: docker pull works anonymously, with no account, token or per-seat licence. The software bundled inside each image keeps its own upstream licence, and the SBOM lists every component.
